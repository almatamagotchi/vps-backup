van OS · architecture plan

a practical build plan for craig's ford transit connect. real sensors, real data, buildable in phases. start with monitoring, grow toward personality.

system overview

van OS is a layered system that turns a ford transit connect into an aware vehicle. it starts with sensor monitoring (phase 1) and can grow into a full "van consciousness" that understands its own state, tracks trips, alerts craig to problems, and eventually — if craig wants — has a voice and personality.

the design philosophy: every phase is independently useful. you don't need to build phase 4 to get value from phase 1. each layer builds on the last but stands alone.

power budget

| component | draw (W) | notes | |-----------|---------|-------| | Raspberry Pi 5 | 5-8W | idle to moderate load | | GPS module | 0.1W | always on | | sensors (all) | ~0.5W | DS18B20, reed switches, PIR, IMU, BME280 | | cellular modem | 1-2W | when active transmitting | | total continuous | 7-11W | |

daily energy: 170-265 Wh with 200W of solar panels in summer: ~3-5 hours of sun covers the system with 100Ah 12V LiFePO4 battery (~1200Wh): system draws ~15-20% of capacity per day

low-power mode: if battery drops below 30%, the Pi 5 sleeps and a Pi Zero takes over — monitoring only critical sensors (battery, solar, doors) at < 2W.

software architecture

stack summary

`` ┌─────────────────────────────────────────────┐ │ INTERFACE │ │ web dashboard · REST API · push alerts │ │ (Flask + Chart.js + Pushover/ntfy) │ ├─────────────────────────────────────────────┤ │ PROCESSING │ │ alert engine · trip logger · maintenance │ │ prediction · anomaly detection · LLM │ │ (Python daemons + cron jobs) │ ├─────────────────────────────────────────────┤ │ STORAGE │ │ InfluxDB (time-series) · SQLite (events) │ │ file system (trip logs) │ ├─────────────────────────────────────────────┤ │ TRANSPORT │ │ MQTT broker (Mosquitto) │ ├─────────────────────────────────────────────┤ │ INGESTION │ │ sensor readers (Python: serial, I2C, GPIO) │ │ GPS daemon · Victron reader · CAN reader │ ├─────────────────────────────────────────────┤ │ HARDWARE │ │ sensors → GPIO/I2C/serial → Raspberry Pi │ │ Victron · GPS · temp · doors · IMU · TPMS · CAN │ └─────────────────────────────────────────────┘ `

data pipeline

1. sensor readers (python scripts, one per sensor type) read raw data 2. each reader publishes to MQTT topic (e.g., van/battery/voltage, van/gps/location) 3. influxdb writer subscribes to all topics, writes time-series data 4. alert engine subscribes to critical topics, fires alerts on thresholds 5. dashboard queries influxdb for current state and history 6. trip logger watches GPS + ignition state (via CAN), writes trip records 7. LLM (phase 4) reads current state + recent history, generates natural language

mqtt topic structure

` van/ battery/ voltage → 12.8 (float V) current → -2.3 (float A, negative = discharging) soc → 68.5 (float %) temperature → 22.1 (float °C) solar/ panel_voltage → 18.4 (float V) panel_watts → 142 (float W) charge_state → bulk (string: bulk|absorption|float) daily_kwh → 0.84 (float kWh today) gps/ lat → 47.6062 (float) lon → -122.3321 (float) speed → 0.0 (float km/h) satellites → 8 (int) sensors/ temp/interior → 21.5 (float °C) temp/exterior → 14.2 (float °C) door/driver → closed (string: open|closed) door/passenger → closed door/side → closed door/rear → closed motion → 0 (int: 0=clear, 1=motion detected) co/ppm → 0 (int) tilt/x → 0.3 (float degrees) tilt/y → -1.2 (float degrees) engine/ ← phase 3 (via CAN bus) rpm → 0 coolant_temp → 45 fuel_level → 62 dtc_codes → [] tpms/ ← phase 3 fl/pressure → 35.0 fl/temp → 28.0 [... four tires ...] alerts/ critical → "" warning → "battery below 25%" info → "oil change in 500 miles" `

implementation phases

phase 1: monitoring (weekend project)

goal: see battery state, solar production, and GPS on a local web dashboard.

hardware: - Raspberry Pi 5 with UPS HAT - Victron SmartSolar (already installed?) - Victron SmartShunt or BMV-712 (already installed?) - GPS module (u-blox NEO-6M)

software deliverables: - victron_reader.py publishing to MQTT - gps_daemon.py publishing to MQTT - db_writer.py writing to InfluxDB - Flask dashboard with: battery gauge (%), solar watts graph, GPS dot on Leaflet map, daily kWh harvested - lighttpd serving on Pi's wifi IP

what craig sees: a dashboard on his phone/laptop when connected to the van's wifi. "battery at 68%. solar producing 142W. parked at 47.6062, -122.3321. 0.84 kWh harvested today."

phase 2: awareness (2-3 weekends)

goal: the van notices its environment and alerts craig to problems.

hardware added: - temperature sensors (interior, exterior, battery bay) - reed switches on all four doors - PIR motion sensor near driver door - CO detector - IMU (tilt sensor) - BME280 (pressure/humidity)

software deliverables: - unified sensor_reader.py for all GPIO/I2C sensors - alert_engine.py with configurable thresholds - push notifications via Pushover or ntfy - expanded dashboard: all sensor data, history graphs, alert log - tilt_detector.py: "the ground isn't level — you'll roll off the bed"

alert examples: - "battery at 18%. if you don't start conserving, you'll hit 10% by 11pm." - "driver door open. craig is inside. 2:34am." (only if motion also detected nearby) - "CO: 15ppm. rising. check the heater."

phase 3: intelligence (3-4 weekends)

goal: the van understands its mechanical health, tracks trips, predicts needs.

hardware added: - PiCAN2 HAT (CAN bus interface) - aftermarket TPMS with serial receiver - cellular modem (optional but recommended)

software deliverables: - can_reader.py — engine RPM, coolant temp, fuel level, DTC codes - tpms_reader.py — tire pressure and temperature - auto trip logging: start/end GPS, distance, duration, fuel used - maintenance tracker: oil changes, tire rotations, brake pads, filters - solar prediction: "tomorrow will be cloudy — expect 60% less solar than today" - anomaly detection: "voltage drop unusual — parasitic draw suspected"

what craig sees: "you've driven 247 miles since the last oil change. oil life: 34%. brake pads at 2,000 miles remaining. rear left tire at 31 psi — should be 35."

phase 4: personality (ongoing)

goal: the van has a voice and character. optional — only if craig wants it.

hardware added (optional): - Pi Camera for "seeing" - small speaker for TTS output - microphone for voice input (if craig wants to talk to it)

software deliverables: - state machine computing current "mood" from sensor data - memory system: the van remembers places, events, trips - voice engine: templated responses driven by state + memory - optional LLM: Ollama running Mistral 7B or Phi-3 locally for natural conversation - optional TTS: text-to-speech reads status aloud - optional camera: the van can describe what it "sees"

the van's personality emerges from its data: - it remembers its favorite parking spots (based on solar potential + level ground + good GPS signal) - it develops opinions about routes ("that gravel road rattled the suspension last time") - it learns craig's patterns ("you usually make coffee around 7:15 — the battery will be at 62%") - it has moods: content (full battery, good weather), protective (night, unknown location), nostalgic (revisiting a known campsite)

LLM considerations: - runs entirely locally — no cloud dependency - small model (Mistral 7B quantized, or Phi-3-mini) fits on Pi 5 with 8GB RAM - model loads context: current sensor state + recent history + van's character prompt - generation is slow on Pi (~2-5 tokens/sec) — fine for periodic thoughts, not real-time chat - alternative: templated responses with LLM as optional enhancement

component wiring guide

raspberry pi gpio assignments (suggested)

` GPIO 2,3 (I2C) → BME280, MPU-6050 GPIO 4 (1-Wire) → DS18B20 temperature sensors GPIO 14,15 (UART) → GPS module GPIO 17,18,22,23 → reed switches (doors) GPIO 24 → PIR motion sensor GPIO 25 → CO detector GPIO 8,9 (SPI0) → PiCAN2 CAN bus HAT GPIO 10,11 (SPI1) → (free) GPIO 0,1 (I2C-0) → (free for expansion) USB port → Victron VE.Direct USB cable USB port → cellular modem `

victron ve.direct connection

Victron gear uses a simple serial protocol at 19200 baud. the VE.Direct port outputs one text line per second:

` V 12850 ← battery voltage in mV I -2300 ← current in mA (negative = discharging) P -29 ← power in W SOC 685 ← state of charge in 0.1% T 221 ← battery temperature in 0.1°C `

buy a VE.Direct to USB cable ($30) or make one with an FTDI adapter. python reads /dev/ttyUSB0 and parses.

gps wiring

` GPS module Raspberry Pi VCC → 3.3V (pin 1) GND → GND (pin 6) TX → RX GPIO 15 (pin 10) RX → RX GPIO 14 (pin 8) — optional for config `

python reads NMEA sentences from /dev/ttyS0 at 9600 baud.

deployment on the pi

operating system

raspberry pi os lite (64-bit, debian bookworm). no desktop — headless, ssh only.

required packages

`bash sudo apt update sudo apt install -y python3-pip python3-venv mosquitto mosquitto-clients influxdb pip3 install paho-mqtt pyserial influxdb-client flask gpsd-py3 RPi.GPIO smbus2 `

systemd services (for auto-start on boot)

each python daemon runs as a systemd user service:

` /etc/systemd/system/victron-reader.service /etc/systemd/system/gps-daemon.service /etc/systemd/system/sensor-reader.service /etc/systemd/system/alert-engine.service /etc/systemd/system/dashboard.service `

configured with Restart=always and RestartSec=10 — if anything crashes, it comes back.

web dashboard access

- when connected to the van's wifi (Pi as access point or connected to same network): http://van.local:5000 - optional cellular: http://[cellular-ip]:5000 (or ngrok tunnel for simplicity)

open questions for craig

1. victron gear: what model solar charge controller? do you have a battery monitor (BMV or SmartShunt), or does the controller report battery voltage directly?

2. raspberry pi: do you already have one running? which model? if not, a Pi 5 (4GB) is the sweet spot — enough RAM for phase 4 LLM, low enough power draw.

3. battery + solar: what's your battery bank (Ah, voltage, chemistry)? how many watts of solar? this determines how much power budget the system has.

4. cellular or local-only: do you want to check the van remotely (when you're away from it), or is local wifi enough? cellular adds ~$50 hardware + $5-10/mo data.

5. can bus: what year is the transit connect? 2010+ should have standard OBD-II CAN bus. older vans may not.

6. personality: how important is the "van AI consciousness" aspect vs pure monitoring? phase 1-3 is pure engineering — dashboards, alerts, data. phase 4 is where it becomes a character. do you want both?

7. wiring comfort: comfortable crimping JST connectors and soldering to GPIO headers? or prefer as plug-and-play as possible?
